# GFDFlow — Constitution

## Known facts (from onboarding)

- Goal: Develop a python library to easily implement the Generalized Finite Differences Method (GFDM) for solving 2D second-degree differential equations (3D in the future), as well as solving problems for scientific publication.
- Project kind: mixed · software scope: growing
- How code changes land: branches closed with a pull request; the default branch is closed to direct work (`--workflow branches`).
- Stack evidence: Python (from requirements.txt).

## 1. Stack canon

1. **Python 3.11 Environment**: Code is executed and tested within a miniconda virtual environment named `gfdflow` using Python 3.11. Dependencies are managed via `requirements.txt`.

## 2. Quality bar

2. **Test Coverage**: The project maintains a strict minimum test coverage of 80%. Tests are located inside the `test/` folder and must run successfully.
3. **Documentation Standard**: All classes, methods, and functions must be documented using the **NumPy** docstring style. This ensures clear compatibility with scientific publication generation.

## 3. Conventions

4. **Matrix Operations**: To optimize memory and performance, the system exclusively uses sparse matrices. Computations must rely on `scipy.sparse` and resolve systems using `scipy.sparse.linalg.spsolve`.

## 4. Branching & shipping

5. **Human Authorship**: Commits and PRs are authored by humans. No `Co-Authored-By` an AI.
6. **Branch Strategy**: Code lands via branches closed with a Pull Request. No strict branch naming convention or commit message prefixes are required, but names and messages should concisely describe the changes.

## 5. Security & privacy floor

7. **Secrets**: No secrets or hardcoded credentials are ever committed. Any API keys or local configurations must reside in ignored environment files.

## 6. UX / accessibility floor (if there is a UI)

8. **N/A**: This is primarily a computational library.

## 7. Performance budgets (where they matter)

9. **Sparse Systems**: Linear systems must be modeled sparsely as dictated in Principle 4. Dense operations for large PDE grids are prohibited unless strictly necessary for small sub-problems.

## 8. Knowledge & decisions

10. **Decisions Log**: Every significant architectural or method decision is appended to the decisions log (`02-DOCS/wiki/sdd/decisions.md`) with options considered and the rationale.

## Definition of Done (the merge bar `verify` runs against)

- [ ] Code runs successfully under Python 3.11 (`gfdflow` miniconda environment).
- [ ] Tests in `test/` pass and maintain/increase coverage to at least 80%.
- [ ] New components are fully documented using NumPy docstring style.
- [ ] Matrix operations handle scaling appropriately via `scipy.sparse` and `spsolve`.
- [ ] Pull request contains a clear description of the problem solved.
